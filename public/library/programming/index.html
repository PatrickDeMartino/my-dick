1. Start here: make something small

Programming means describing an exact sequence of changes to data. A program does not understand your intentions; it follows instructions. AI can draft those instructions, explain unfamiliar code, and help find mistakes. You remain responsible for deciding what should happen and checking what actually happens. Start with a small win: a button that counts clicks. Then save the number. Then turn it into a tiny inventory. Each step gives you a working thing you can understand.

Create a folder called first-world. Inside it create index.html in a plain-text editor. Copy the complete example below, save it, and open it. You do not need an account, payment, internet connection, or AI service for this first exercise. Change the heading and button label, save, and refresh. Your first skill is connecting an edit to an observable result.

2. Your first complete program

The browser reads HTML as the document structure, CSS as the appearance, and JavaScript as behavior. An element’s id gives code a stable way to find it. Here the state is one number. Each click changes that number and then draws its new value. Type the code yourself at least once; punctuation errors teach you how precise instructions need to be.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>My first world</title>
<h1>My inventory</h1>
<p>Cans: <strong id="count">0</strong></p>
<button id="add">Add a can</button>
<script>
let count = 0;
const output = document.querySelector('#count');
document.querySelector('#add').addEventListener('click', () => {
  count += 1;
  output.textContent = String(count);
});
</script>

Exercise: add a second button that removes a can without allowing a negative count. Then display “empty” when the count is zero.

3. Values, decisions, and repeated work

A variable is a name for a value. Use const for a binding you do not reassign, and let when you will assign a new value. Numbers support arithmetic; strings hold text; booleans are true or false. Arrays hold ordered lists. Objects collect named properties. An inventory might be [{id:'can', count:3}, {id:'brain', count:1}]. Distinguish an object’s stable ID from the label shown to a player.

An if statement chooses a branch. A loop repeats work. A function names a reusable operation. Write a function addItem(inventory, id) that returns a new inventory. First handle an empty inventory. Then handle an existing item. Test both. Avoid changing data in two unrelated places; a single change function is easier to reason about.

Practice: write clamp(value, min, max). Try values below, inside, and above the range. Explain to a friend why Math.max(min, Math.min(max, value)) works. Then add tests for negative numbers and decimal values. Decide explicitly what should happen with invalid input.

4. Read a project before changing it

Find the entry point, the dependency list, the source folder, the public assets, and the build output. Source is the editable recipe. Build output is the prepared program. Dependencies are reusable libraries that the recipe needs. Do not hand-edit generated bundles unless you are intentionally repairing an archived artifact and have documented why.

In this project, app contains pages and components. app/world holds the shared model catalog, factories, and physics runtime. public contains images, 3D files, sounds, and the offline library. docs explains the structure. The catalog maps stable IDs to the function or file that makes a model. Following one ID from catalog to factory to screen is a good first reading exercise.

Before editing, write the behavior you want in one sentence. Identify the smallest place that owns it. Read callers of that code so you understand the effect of changing its contract. Keep a note of assumptions. A useful change is one you can explain and undo.

5. Use AI as a collaborator

Give the assistant a specific problem, the relevant files, constraints, and an observable success condition. For example: “In the asset catalog, add a search field that matches labels and categories, ignoring capitalization. Preserve the current category buttons. Show an empty-state message when nothing matches. Verify that searching for rat finds Lab Rat.”

Ask for an explanation of the proposed change before accepting a large rewrite. Prefer one coherent task at a time. Tell the assistant which files it may change, whether network access is allowed, and what must remain compatible. Never paste passwords, private keys, or customer secrets into a prompt. Store secrets outside source code.

After a generated change, inspect the diff. Run the app. Exercise the normal path, an empty input, an invalid input, and a repeated action. Ask the assistant what it did not test. If it claims a test passed, look for the actual test result. AI output can be useful and still be wrong; verification is part of programming, not a sign that collaboration failed.

6. Debug with evidence

Describe the symptom precisely: what you did, what you expected, and what happened. Reproduce it with the smallest steps you can find. Open the browser’s developer tools and read the first relevant error. Later errors may be consequences of the first one.

Log a small number of meaningful values at the boundary where the program changes state. If an object disappears, check its position, visibility, scale, parent, and whether it has been removed from the scene. If a button does nothing, check whether its handler runs and whether the correct state changes. If a request fails, inspect its URL and response status. Do not fix three theories at once; change one thing and rerun the reproduction.

Practice: deliberately misspell the counter element’s ID. Read the error, fix the typo, and explain the cause. Then make the count a string and observe what adding 1 does. Debugging gets easier when you can predict how a language treats a value.

7. Save changes with version control

Git records snapshots of your source. A repository contains its history. A branch gives a change a place to develop before it joins the main line. A commit should describe a coherent result: “Add searchable asset catalog” is more useful than “stuff.” A diff shows exactly what changed.

Before a big edit, confirm the current folder and save a checkpoint. Read the diff before committing. Keep generated output and downloaded caches out of source history unless the project intentionally tracks them. Never commit secrets. If you discover a secret in history, removing the latest line is not enough; revoke the credential and follow the hosting provider’s guidance.

Practice on a disposable copy: make one text change, inspect it, commit it, make another change, and restore the first file from the earlier commit. Learn recovery before you need it. The offline bundle includes a source copy and a manifest so you can compare future changes without guessing which files belong together.

8. Build a tiny 3D world

A scene is a collection of objects. A mesh combines geometry, which describes shape, with a material, which describes how light interacts with the surface. A camera determines the view. A renderer draws that view. Position moves an object; rotation turns it; scale changes its size. Parent-child relationships make local coordinates useful: moving a character carries its hand, and moving the hand carries a held can.

Start with one cube, one floor, one light, and one camera. Make the cube fall. Add a floor collision. Then replace the cube with a model while keeping the same movement contract. Avoid coupling the identity of a mesh to its behavior. In Triptotropic, a stable asset ID chooses the model and a body role chooses how it behaves.

A model may face positive Z in its local coordinates while the camera looks in a different direction. To throw where the character faces, transform the local forward vector by the character’s world rotation. Do not silently substitute the camera’s direction. This distinction is what allows a character to turn toward you and throw back toward the camera.

9. Physics without frame-rate surprises

Velocity describes change in position per second. Acceleration describes change in velocity per second. With a small timestep dt, update velocity with acceleration multiplied by dt, then update position with velocity multiplied by dt. The shared runtime uses fixed simulation steps so a faster display does not make objects fall faster.

A collision shape is an approximation used for contact calculations. It can be simpler than the visible mesh. A sphere is cheap to test; a detailed moving triangle mesh is expensive. Choose accuracy where it matters, and document approximations. Ragdolls add joints or distance constraints between parts. More polygons alone do not improve physics.

Practice: spawn the same object twice at the same height, set gravity to Earth, and time the fall. Repeat at different display resolutions. Then use zero gravity and apply an impulse. Check whether the object continues moving. A physics test should ask about behavior, not repeat the implementation line for line.

10. Data, saving, and compatibility

Save the information needed to rebuild a scene, not the entire renderer. A useful scene record contains a format name, a version, global physics settings, and objects with asset IDs, roles, positions, rotations, and scales. Validate imported data before using it. Reject unknown formats clearly. Limit object counts and numeric ranges so a mistaken file cannot freeze the app.

Browser storage belongs to one device and origin. It is useful for preferences but is not a shared database. Exported files are portable. A server database is appropriate when multiple people must share or synchronize information. Decide which of these you need before building a save feature.

The later Hex builder integration can consume the scene format if both projects agree on units, axes, asset IDs, and role semantics. Write those agreements down. When a model changes, preserve its ID if it still represents the same thing. When behavior changes incompatibly, increase the format version and provide a migration.

11. Tests, performance, and release

A good test catches a mistake that would matter to someone using the program. Test important calculations, save/load round trips, role changes, missing assets, and a few complete user journeys. Manual visual checks still matter for 3D art, camera framing, touch controls, and readable menus.

Measure before optimizing. A slow frame may come from too many draw calls, too much geometry, expensive shaders, texture memory, or code allocating thousands of temporary objects. Reuse geometry where appropriate. Dispose of GPU resources when a scene is removed. Cap concurrent heavy models. Load large documents only when someone opens them.

Before release, build from the exact source you intend to publish. Test navigation and the main interactions. Keep the prior version available for rollback. Verify that the offline package contains its assets and does not need a CDN to start. Online AI, live feeds, and account services need an explicit offline behavior; do not pretend a remote service is available without a connection.

12. A path toward professional work

Progress through complete projects: a counter, a saved inventory, a searchable catalog, a small 3D scene, a scene editor, and then a shared app with a server. For each project, write a short README explaining what it does, how to run it, how to test it, and what is unfinished. Let another person follow the instructions without your help.

Study the fundamentals alongside the projects: data structures, functions, modules, asynchronous work, HTTP, databases, accessibility, security, and testing. Learn one language deeply enough to predict its behavior. Read library documentation instead of relying only on examples. Review code written by other people and explain tradeoffs without insulting their choices.

Professional skill is the ability to deliver understandable, reliable changes repeatedly. There is no single prompt or book that grants it. Keep a notebook of bugs you solved, assumptions you corrected, and designs that became simpler. Your next exercise is practical: add one catalog asset, make it work in all nine roles, export a scene, reload it, and document the result. That small finished contribution is a real step forward.
